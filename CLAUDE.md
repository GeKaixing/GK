# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Gekaixing (个开心) is a Twitter/X-style social platform built on Next.js 16 App Router. Core surface: feed, posts/replies/likes/bookmarks/shares, follow graph, messaging, AI chat, plus an analytics dashboard and blog. Bilingual (en / zh-CN).

`AGENTS.md` (and `AGENTS.Chinese.md`) contains the project's coding-style rules — follow them for style/typing. This file covers architecture: the pieces that span multiple files.

## Commands

```bash

npx prisma studio        # DB GUI
```

## Architecture

### Routing & auth guard

- `app/` is the App Router. **`proxy.ts`** at the repo root is Next 16's middleware (renamed from `middleware`). It refreshes the Supabase session via `utils/supabase/proxy.ts` (`updateSession`) and **redirects unauthenticated users to `/account`** unless the path is in the allowlist. If you change a public route, update this allowlist.
- Supabase SSR clients: server side uses `utils/supabase/server.ts` (create a fresh client per function — do not hoist to a module global), browser side uses `utils/supabase/client.ts`.
- Note the env-var naming is inconsistent across clients: `client.ts` reads `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_DEFAULT_KEY`, while `server.ts` and `proxy.ts` read `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Keep both set.

### Database (Prisma)

- **All database access goes through Prisma — it is the single source of truth for data tables.** Never add a direct DB driver or another ORM for app data. Rationale: the DB may be swapped later (Prisma adapter-pg already abstracts the connection), so nothing should depend on PostgreSQL specifics beyond what Prisma models.
- **Supabase only handles Supabase-specific things: Auth (SQL triggers/hooks), RLS policies, and Edge Functions.** Do not manage app tables via Supabase CLI migrations (`supabase db push`) or raw SQL against the shared DB — that fights Prisma and causes drift. A `supabase/` directory for those Supabase-only pieces is fine, but app schema changes go through `prisma/schema.prisma`.
- `prisma/schema.prisma` defines the models. The datasource has **no `url`** — the client is constructed with a `@prisma/adapter-pg` (`PrismaPg`) connection pool in `lib/prisma.ts`, driven by `DATABASE_URL`. All DB access goes through the single exported `prisma` instance.
- The client is generated by the new `prisma-client` provider into `generated/prisma` (not `node_modules/@prisma/client`). Enums are imported from `@/generated/prisma/enums`. **After editing the schema, run `npx prisma generate`.**
- Key models: `User`, `Post` (replies are `Post` rows with `parentId`/`rootId`, self-relation; counts are denormalized `likeCount`/`replyCount`/`shareCount`/`starCount`), `Like`/`Bookmark`/`Share` (unique per user+post), `Follow`, `Conversation`/`Message`/`ConversationRead`, `PiSessionFile` (AI chat sessions), `JobPosting`, `UserAction` (analytics event log).

### Feed ranking & caching

- `lib/feed/service.ts` computes the home feed: scores candidate posts by engagement (`log1p` of likes/replies/shares), a time-decay factor, a +10 boost for followed authors, and a behavior-boost map derived from the user's `UserAction` history. Returns a ranked post-ID list.
- `lib/feed/cache.ts` caches the ranked list and page slices in **Upstash Redis REST** (via `UPSTASH_REDIS_REST_URL`/`TOKEN`), 5-min TTL, with a recompute lock and stale-invalidation. If Redis env vars are absent, all cache helpers no-op (`runRedisCommand` returns `null`) and the feed recomputes per request.
- Feed mutations invalidate caches: `invalidateUserHomeFeed(userId)` after a user acts, `invalidateAuthorAudienceFeed(authorId)` fans out to the author's followers. Cursor pagination is exposed through `FeedPage { data, page: { nextCursor, hasMore } }`.

### Analytics pipeline

- **Everything is derived from the `UserAction` table.** Clients/components log events (FEED_IMPRESSION, POST_CLICK, REPLY_CREATE, POST_LIKE, POST_SHARE, POST_BOOKMARK, FOLLOW, DWELL) with a JSON `metadata` string that carries `{ source, kind }` (e.g. `{"source":"feed_card","kind":"profile_enter"}`). The dashboard code parses this metadata, so the `kind`/`source` keys are part of the contract.
- `lib/dashboard/service.ts` aggregates UV/PV, DAU/WAU/MAU, D1/D7 cohort retention, funnel, traffic sources, audience and content segments for the `/dashboard` routes. Functions are wrapped in React `cache()` and return typed shapes from `lib/dashboard/types.ts`; each returns an all-zero default on missing user or error. Adding a metric means: log the event where it happens → extend an aggregation here → add types → render in `app/dashboard/*`.
- Dashboard navigation is data-driven from `lib/dashboard/navigation.ts`.

### OSP protocol layer (v3.0.0)

Gekaixing is the **reference implementation of OSP (Open Social Protocol)** — the first "Country" (id `gkx`). The spec lives in `rfc/` (16 RFCs). **Cross-country federation is not implemented yet**; v3.0.0 lands the protocol core: identity, passport, signed event ledger, data ownership, capability, feed-provider, customs.

- **`lib/osp/` is the internal OSP SDK** (server-only): `keys.ts` (Ed25519 canonicalize/sign/verify, deterministic derivation), `country.ts` (Country gkx + `OSP_COUNTRY_SECRET`), `actor.ts` (`Actor` is 1:1 with `User`; the GKX AI is a service actor `actor_gkxi_ai`), `passport.ts` (`issuePassport`/`verifyPassport`/`ensureCitizen` — the identity bootstrap entry), `event.ts` (signed append-only ledger), `capability.ts`, `customs.ts`, `did.ts`, `object.ts`.
- **Key posture = country-managed signing.** Ed25519 keys are derived deterministically (HMAC) from `OSP_COUNTRY_SECRET` (`openssl rand -hex 32`) — private keys are never stored at rest. **Losing the secret invalidates every passport**; back it up. Actor keys are derived per-actor; only public keys are persisted (`Country.publicKey`, `Passport.publicKey`).
- **Models:** `Country`, `Actor` (userId is `SetNull` on user delete — the Actor + ledger survive account deletion), `Passport`, `OspEvent` (the **signed protocol ledger**, immutable, no cascade; distinct from `UserAction` analytics — do NOT unify them), `Capability`. `Post.visibility` is **schema-only** (RFC-005), not enforced yet.
- **Identity bootstrap:** `ensureCitizen(userId)` is called in the two User-creation points (`app/api/signup/route.ts`, `app/auth/callback/route.ts`) and backfilled by `scripts/bootstrap-osp.ts` (idempotent — run at every deploy after `prisma db push`).
- **Event ledger:** mutation routes record `OspEvent`s alongside `logUserAction` (post/reply/like/bookmark/share/follow/message/account-delete + lifecycle events). Message events carry **no content** (RFC-008 private-data posture). Verify: `GET /api/osp/events/verify` and `GET /api/osp/passport/verify`.
- **Feed providers (RFC-014):** `lib/feed/providers/` — `registry.ts` + `following.ts` + `foryou.ts` (the algorithmic path, moved verbatim from `service.ts`). `lib/feed/service.ts` is the thin orchestrator (`getFeedProvider(tab).compute(userId)`). Transparency via `GET /api/feed/providers`.
- **Customs (RFC-010):** `lib/osp/customs.ts` defines the admission pipeline + decision types (ALLOW/RESTRICT/DENY/QUARANTINE); only the pass-through `allowingCustoms` is registered, so post/reply creation is behaviorally unchanged.
- **Capabilities (RFC-015):** `CREATE_POST`/`SEARCH` (+`MODERATE` for admins) are seeded per actor; the AI chat's `webSearch`/`fetchUrl` are gated by the AI service actor's `SEARCH` capability (`lib/ai/pi.ts`).
- **Data ownership (RFC-008):** `GET /api/user/export` returns a full signed export (manifest digest + Country signature); account deletion (`DELETE /api/user`) revokes passport/capabilities, records `ACCOUNT_DELETED`, and cleans tables Prisma can't cascade (`PiSessionFile`, `ChatAISession`, `Follow` both directions, orphaned conversations).

### OSP federation (RFC-009 Federation + RFC-011 Recognition)

Peer "Countries" discover, recognize and exchange signed content. **Inbound auth = signature verification** — no shared secret; the peer's public key is the credential.

- **Models:** `RemoteCountry` (peer id/name/publicKey/federationEndpoint), `Recognition` (directional, `fromCountryId`=gkx; default UNKNOWN; RECOGNIZED/TRUSTED admit), `FedDelivery` (outbound queue, payload persisted so retries are self-contained), `FedInbox` (inbound receipt log, `eventId` unique = idempotency), `FedObject` (admitted remote content — **never mixed into `Post`**, sanitized on receipt), `RemoteActor` (remote identity cache).
- **`lib/osp/federation.ts`:** `buildWellKnown`/`fetchCountryWellKnown` (discovery), `getRecognition`/`setRecognition`/`isAdmitting`, `enqueueFederationDelivery` (broadcast signed content events to recognized peers; fire-and-forget), `deliverPending` (worker, `attempts^2` min backoff), `handleInboundFederation` (verify → recognition gate → Customs → sanitize → store), `resolveRemoteActor`/`buildRemoteActorProfile` (DID resolution).
- **Discovery:** served at `/.well-known/osp` via a **rewrite** (`next.config.ts` — App Router ignores dot-prefixed folders); added `/.well-known` and `/gekaixing/federated` to the proxy allowlist.
- **Routes:** `POST /api/fed/inbox` (202/401/200-duplicate), `POST /api/fed/deliver` (admin or `FED_DELIVERY_SECRET` Bearer), `GET /api/fed/feed`, `GET /api/fed/resolve?did=`, `GET /api/fed/actors/[countryId]/[actorId]`, `POST /api/admin/federation` (admin: add/recognize). Only `post`/`reply` POST enqueue outbound content (likes/follows/messages do NOT federate — RFC-012 deferred; messages are private).
- **CLI:** `scripts/fed-add-country.ts <host>` (discover + add peer), `scripts/fed-recognize.ts <countryId> --state=RECOGNIZED`, `scripts/fed-deliver.ts` (flush queue). Use `npx tsx --env-file=.env.development.local`.
- **Security:** inbound content sanitized with `sanitize-html` (scripts/XSS stripped, `data-*` kept for embeds); inbox caps body at 1MB; unknown/unrecognized peers are rejected/denied; remote content is read-only in v1.

### Cross-country social graph (RFC-012)

Federated content is interactive: a local user can follow remote actors, and like/reply to remote posts. Remote relationships live in **separate models** — never merged into the local `Follow`/`Like`/`Post` tables.

- **Models:** `RemoteFollow` (we → remote actor), `RemoteFollower` (remote actor → our user), `RemoteLike` (we → remote post), `RemoteLikeInbound` (remote actor → our post), `RemoteReply` (our local Post → remote parent). All unique-constrained to prevent dupes.
- **Delivery:** replies reuse the existing **broadcast** (`enqueueFederationDelivery`, `parent_id` = remote post); follows/likes use **targeted** delivery (`enqueueTargetedDelivery`) to the post/actor's country. Inbound FOLLOWED/POST_LIKED are handled by `handleInboundFederation` → `RemoteFollower`/`RemoteLikeInbound` (deduped, signature/recognition-gated).
- **Helpers:** `followRemote`/`unfollowRemote`/`likeRemote`/`unlikeRemote` (each records the relationship + ledger event + targeted delivery), `isFollowingRemote`, `isRemoteLiked`, `getRemoteFollowerCount`, `getRemoteLikeCount`, `getRemotePostLikeCount`, `buildFedInteractionMaps` (batch interaction state for feed/page).
- **Routes:** `POST/DELETE /api/fed/follow`, `POST/DELETE /api/fed/like`, `POST /api/fed/reply` (local Post + RemoteReply + broadcast). `GET /api/fed/feed` returns per-item `isFollowing`/`likedByMe`/`remoteLikeCount`.
- **UI:** `FedPostCard` is interactive (follow button, like, reply dialog via `MinimalTiptapEditor`); the status page shows remote replies + a remote-like count; profiles show a remote-follower count. Guests are redirected to `/account` on interaction.

### AI subsystem

- **Users bring their own API key; the app is provider-agnostic (Pi agent + AI SDK).** Provider/key/model live in Supabase `user_metadata` (`ai_provider`, `ai_api_key`, `ai_model`, optional `ai_base_url`), configured in `components/gekaixing/SettingAI.tsx` at `/gekaixing/settings/account`. Legacy `gemini_api_key` / `gemini_model` still work (treated as provider `google`). If no key is set, AI endpoints return 503 and point the user to settings.
- Config resolution: `lib/ai/config.ts` `getUserAiConfig()` maps `user_metadata` → `AiUserConfig` (`lib/ai/types.ts`). Providers are `google` / `openai` / `anthropic` plus `*-compatible` variants (which use `baseURL` — e.g. DeepSeek / GLM via OpenAI-compatible). Model allowlists, `DEFAULT_MODEL`, and `normalizeModel()` / `getModelCandidates()` live in `lib/ai/models.ts` (`OPENAI_COMPATIBLE_PRESETS` ships presets for DeepSeek / GLM / Kimi / MiniMax / OpenRouter). **The candidate-model fallback loop is intended behavior** — if the preferred model errors, callers try the rest of the allowlist.
- `lib/ai/providers.ts` `buildLanguageModel()` maps a provider to an AI SDK `LanguageModel` (`@ai-sdk/google` / `@ai-sdk/openai` / `@ai-sdk/anthropic`).
- **Two AI call paths:**
  - `app/api/chat/route.ts` — **Pi agent chat** (`@earendil-works/pi-agent-core` / `pi-ai`): `createPiAgent()` (`lib/ai/pi.ts`) builds an agent with Pi-native tool calling and registers `webSearch` / `fetchUrl` (`lib/ai/search.ts`); `lib/ai/pi-chat.ts` adapts Pi sessions to the chat UI; `lib/ai/pi-session.ts` + `lib/ai/pi-fs.ts` persist sessions to Postgres via the Prisma `PiSessionFile` table (per-user, namespaced by `cwd`). Returns an SSE-style `text/plain` stream with the session id in `X-Session-Id`; `maxDuration = 60`. (The legacy `ChatAISession` / `ChatAIMessage` models are unused by this path.)
  - `app/api/post/ai/route.ts` — non-streaming content generation via `generateAiText()` (`lib/ai/text.ts`, built on the Vercel AI SDK `ai` package), `mode: "generate" | "polish"`, maps provider errors to HTTP statuses.
- The root `news.ts` is a commented-out Cloudflare Worker for news ingestion; live news comes from `app/api/news/*` routes (NewsAPI via `NEXT_PUBLIC_NEWs_key`).

### Monetization

- Premium/subscription state lives on `User` (`isPremium`, `stripeCustomerId`, `stripeSubId`, `subscriptionStatus`, `premiumExpiresAt`, `premiumGraceEndsAt`). Stripe checkout and webhook live at `app/api/stripe/*`; `lib/stripe.ts` is the configured client. The webhook is the source of truth for subscription state transitions.

### i18n

- next-intl with `messages/en.json` and `messages/zh-CN.json`. There is **no locale segment in URLs and no locale middleware** — `i18n/request.ts` resolves the locale from the request, falling back to the `NEXT_LOCALE` cookie, then `en`. Components use `useTranslations` / `getTranslations`.

### Notifications

- There is no notifications table. Mentions are derived on the fly in `app/gekaixing/layout.tsx` by counting posts containing `@<userid>` (case-insensitive). The "last seen" cursor is an httpOnly cookie (`gkx_notifications_last_seen_at`) set by `app/api/notifications/seen/route.ts`. The badge count is passed into `Sidebar`/`MobileHeader` from the layout.

### Components & state

- `components/ui/` = shadcn/ui primitives (new-york). `components/gekaixing/` = app-specific components. `components/ui/minimal-tiptap/` is a large vendored rich-text editor used for post composition (content is stored as HTML in `Post.content`; images/videos are embedded via data attributes rather than dedicated columns).
- Client state is Zustand in `store/` (`user`, `post`, `reply`, `postModal`, `post_images`, `AiSessions`). Post images/media upload to the Supabase `images` bucket via `utils/function/uploadImageToSupabase.ts` / `uploadMediaToSupabase.ts`.

### Content

- `/blog/[slug]` renders the personal-blog markdown from `markdown/`. `/notion/[slug]` renders Notion pages via `lib/notion.ts` + react-notion-x. SEO lives in `app/sitemap.ts` and per-page metadata.

### Testing

- Vitest (`vitest.config.ts` aliases `@`). Tests sit next to the code (e.g. `app/api/post/ai/route.test.ts`, `app/api/news/hot-us/route.test.ts`, `lib/ai/*.test.ts`); the post/ai route test mocks `@/utils/supabase/server` and `@/lib/ai/text` — follow that mock pattern for new route tests. `npm run test` runs all; pass a path to run one file.
