# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Gekaixing (个开心) is a Twitter/X-style social platform built on Next.js 16 App Router. Core surface: feed, posts/replies/likes/bookmarks/shares, follow graph, messaging, AI chat, plus an analytics dashboard and blog. Bilingual (en / zh-CN).

`AGENTS.md` (and `AGENTS.Chinese.md`) contains the project's coding-style rules — follow them for style/typing. This file covers architecture: the pieces that span multiple files.

## Commands

```bash
npm run dev          # dev server (Turbopack, port 3000)
npm run build        # production build
npm run start        # production server
npm run lint         # ESLint (next lint)
npm run test         # Vitest (run all)
npm run init:storage # create the Supabase "images" storage bucket

npx vitest run <path>    # run a single test file, e.g. npx vitest run app/api/post/ai/route.test.ts
npx tsc --noEmit         # type-check only
npx prisma generate      # regenerate client into generated/prisma
npx prisma db push       # push schema to dev DB
npx prisma migrate dev   # create/apply a migration
npx prisma studio        # DB GUI
```

## Architecture

### Routing & auth guard

- `app/` is the App Router. **`proxy.ts`** at the repo root is Next 16's middleware (renamed from `middleware`). It refreshes the Supabase session via `utils/supabase/proxy.ts` (`updateSession`) and **redirects unauthenticated users to `/account`** unless the path is in the allowlist. If you change a public route, update this allowlist.
- Supabase SSR clients: server side uses `utils/supabase/server.ts` (create a fresh client per function — do not hoist to a module global), browser side uses `utils/supabase/client.ts`.
- Note the env-var naming is inconsistent across clients: `client.ts` reads `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_DEFAULT_KEY`, while `server.ts` and `proxy.ts` read `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Keep both set.

### Database (Prisma)

- **All database access goes through Prisma — it is the single source of truth for data tables.** Never add a direct DB driver or another ORM for app data. Rationale: the DB may be swapped later (Prisma adapter-pg already abstracts the connection), so nothing should depend on PostgreSQL specifics beyond what Prisma models.
- **Supabase only handles Supabase-specific things: Auth (SQL triggers/hooks), RLS policies, and Edge Functions.** Do not manage app tables via Supabase CLI migrations (`supabase db push`) or raw SQL against the shared DB — that fights Prisma and causes drift. A `supabase/` directory for those Supabase-only pieces is fine, but app schema changes go through `prisma/schema.prisma`.
- `prisma/schema.prisma` defines the models. The datasource has **no `url`** — the client is constructed with a `@prisma/adapter-pg` (`PrismaPg`) connection pool in `lib/prisma.ts`, driven by `DATABASE_URL`. All DB access goes through the single exported `prisma` instance.
- The client is generated by the new `prisma-client` provider into `generated/prisma` (not `node_modules/@prisma/client`). Enums are imported from `@/generated/prisma/enums`. **After editing the schema, run `npx prisma generate`.**
- Key models: `User`, `Post` (replies are `Post` rows with `parentId`/`rootId`, self-relation; counts are denormalized `likeCount`/`replyCount`/`shareCount`/`starCount`), `Like`/`Bookmark`/`Share` (unique per user+post), `Follow`, `Conversation`/`Message`/`ConversationRead`, `ChatAISession`/`ChatAIMessage`, `JobPosting`, `UserAction` (analytics event log).

### Feed ranking & caching

- `lib/feed/service.ts` computes the home feed: scores candidate posts by engagement (`log1p` of likes/replies/shares), a time-decay factor, a +10 boost for followed authors, and a behavior-boost map derived from the user's `UserAction` history. Returns a ranked post-ID list.
- `lib/feed/cache.ts` caches the ranked list and page slices in **Upstash Redis REST** (via `UPSTASH_REDIS_REST_URL`/`TOKEN`), 5-min TTL, with a recompute lock and stale-invalidation. If Redis env vars are absent, all cache helpers no-op (`runRedisCommand` returns `null`) and the feed recomputes per request.
- Feed mutations invalidate caches: `invalidateUserHomeFeed(userId)` after a user acts, `invalidateAuthorAudienceFeed(authorId)` fans out to the author's followers. Cursor pagination is exposed through `FeedPage { data, page: { nextCursor, hasMore } }`.

### Analytics pipeline

- **Everything is derived from the `UserAction` table.** Clients/components log events (FEED_IMPRESSION, POST_CLICK, REPLY_CREATE, POST_LIKE, POST_SHARE, POST_BOOKMARK, FOLLOW, DWELL) with a JSON `metadata` string that carries `{ source, kind }` (e.g. `{"source":"feed_card","kind":"profile_enter"}`). The dashboard code parses this metadata, so the `kind`/`source` keys are part of the contract.
- `lib/dashboard/service.ts` aggregates UV/PV, DAU/WAU/MAU, D1/D7 cohort retention, funnel, traffic sources, audience and content segments for the `/dashboard` routes. Functions are wrapped in React `cache()` and return typed shapes from `lib/dashboard/types.ts`; each returns an all-zero default on missing user or error. Adding a metric means: log the event where it happens → extend an aggregation here → add types → render in `app/dashboard/*`.
- Dashboard navigation is data-driven from `lib/dashboard/navigation.ts`.

### AI subsystem

- **Gemini is primary; users bring their own API key.** The key and preferred model live in Supabase `user_metadata` (`gemini_api_key`, `gemini_model`). If absent, AI endpoints return 503 and point the user to `/gekaixing/settings/account`. Users can also be directed to set it there via `components/gekaixing/SettingGeminiKey.tsx`.
- Model selection: `lib/gemini-model.ts` defines an allowlist (`GEMINI_MODEL_OPTIONS`), the default, and `normalizeGeminiModel()` (falls back to default for unknown values) plus `getGeminiModelCandidates()` which orders the user's preferred model first. **The fallback loop through candidate models is the intended behavior** — if the preferred model errors, callers try the rest before giving up.
- Two Gemini call paths:
  - `lib/gemini.ts` `generateGeminiText()` — non-streaming, used for content generation (e.g. `app/api/post/ai/route.ts`, which supports `mode: "generate" | "polish"` and maps Gemini errors to HTTP statuses).
  - `app/api/chat/route.ts` — streaming (`generateContentStream`), persists each `ChatAISession` and `ChatAIMessage` to Prisma, returns an SSE-style text stream with the session id in `X-Session-Id`.
- `lib/ai.ts` `streamGLM()` calls Zhipu's GLM API (OpenAI-compatible) and is a second, less-used provider.
- The root `news.ts` is a commented-out Cloudflare Worker for news ingestion; live news comes from `app/api/news/*` routes (NewsAPI via `NEXT_PUBLIC_NEWs_key`).

### Monetization

- Premium/subscription state lives on `User` (`isPremium`, `stripeCustomerId`, `stripeSubId`, `subscriptionStatus`, `premiumExpiresAt`, `premiumGraceEndsAt`). Stripe checkout and webhook live at `app/api/stripe/*`; `lib/stripe.ts` is the configured client. The webhook is the source of truth for subscription state transitions.

### i18n

- next-intl with `messages/en.json` and `messages/zh-CN.json`. There is **no locale segment in URLs and no locale middleware** — `i18n/request.ts` resolves the locale from the request, falling back to the `NEXT_LOCALE` cookie, then `en`. Components use `useTranslations` / `getTranslations`.

### Notifications

- There is no notifications table. Mentions are derived on the fly in `app/gekaixing/layout.tsx` by counting posts containing `@<userid>` (case-insensitive). The "last seen" cursor is an httpOnly cookie (`gkx_notifications_last_seen_at`) set by `app/api/notifications/seen/route.ts`. The badge count is passed into `Sidebar`/`MobileHeader` from the layout.

### Components & state

- `components/ui/` = shadcn/ui primitives (new-york). `components/gekaixing/` = app-specific components. `components/ui/minimal-tiptap/` is a large vendored rich-text editor used for post composition (content is stored as HTML in `Post.content`; images/videos are embedded via data attributes rather than dedicated columns).
- Client state is Zustand in `store/` (`user`, `post`, `reply`, `postModal`, `post_images`, `AiSessions`). Post images/media upload to the Supabase `images` bucket via `utils/function/uploadImageToSupabase.ts` / `uploadMediaToSupabase.ts`.

### Content

- `/blog/[slug]` renders the personal-blog markdown from `markdown/`. `/notion/[slug]` renders Notion pages via `lib/notion.ts` + react-notion-x. SEO lives in `app/sitemap.ts` and per-page metadata.

### Testing

- Vitest (`vitest.config.ts` aliases `@`). Only one test exists (`app/api/post/ai/route.test.ts`); it mocks `@/utils/supabase/server` and `@/lib/gemini` — follow that mock pattern for new route tests. `npm run test` runs all; pass a path to run one file.
